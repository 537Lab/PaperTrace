# INV-07 answer compaction test proposal

D supplies the approved evidence and token policy. B uses the existing selection order to drop whole evidence records from the end of the selected set. At the compaction threshold, B rebuilds and counts the request after each removal. The question and versioned system text remain byte identical in the final serialized request. Only the records in that request may contribute sent IDs or citation aliases.

The cases exercise the existing gateway and the real PaperQA2 answer path with controlled token counts and a network fence. Each case runs through the default product gateway and the opt-in fixed-ID gateway. Two records remain below 9,000. A count of 9,000 triggers the first reduction when two records are available. Reversed priorities test that the first record survives when the count falls from 12,001 to 7,000. Both paths make one model attempt, with runtime IDs for default use and fixed IDs for evaluation. The evaluation capture matches the call arguments. Sent runtime IDs and evaluation citation aliases match the retained record.

A single record at 9,000 or 12,000 may be sent when it fits the configured input cap. The test proposes a structured `answer_compaction_floor` event carrying `input_tokens` and `input_cap` for that condition. This event is the proposed observation point for review. An irreducible request over the input cap, one whose required content exceeds the cap, or one that loses all evidence stops before capture and model entry. The smaller-window cases use an 8,500-token input cap representing the allowance remaining after the model's output reservation. Provider-specific window discovery and exact tokenizer behavior require separate verification with the selected runtime. No live calls are required for this proposal.
