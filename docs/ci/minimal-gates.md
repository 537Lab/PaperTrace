# Five-person team minimal gate route

This page is a short index; it does not introduce a separate certification platform, a duplicate approval contract, or a permanent BLOCKED rule. All six course gate categories are retained; for the engineering implementation and entry points see [README](README.md).

- **Test approval**: the plan is approved by the supervising student first → OpenCode prepares module tests only → a non-implementer Approves the exact test SHA on GitHub → only then is the implementation developed. A test proposal may stay open/RED, and merging red tests into main is not required; the implementation PR references `Test approval PR: #N`. The same non-implementer may approve the tests and do the final review; all four people are not required to be present. See [test-approval](test-approval.md).
- **Semantic quality**: applies only to diffs concerning product AI/prompt/model; after the real data/model/budget is approved, run the fixed set and score each case independently, bound to the GitHub run/artifact/review; a locally written PASS is not accepted. See [evaluation](../../test/evaluation/README.md).
- **Full regression**: the three sources — team offline, runtime, and upstream `tests/`+`packages/` — are added; unmarked tests are collected too, and live items are listed and BLOCKED without authorization; missing dependencies/skip/timeouts never equal passing. Do not use `-m offline` to omit other tests. See [full-regression](full-regression.md).
- **Static/Schema/disclosure**: run the actual verifiers; a static/structural pass does not mean security certification, feature completion, or completed student human review.

## The simplest realistic route for private-repository protection

On 2026-11-14 the classic protection API against `537Lab/PaperTrace` returned 403 in a real test (Pro or public required). Stay private; do not upgrade to a paid plan, migrate the repository, or build in-house authentication. For now manage merges manually with visible CI + one non-author review, and **do not claim enforced blocking is in effect**. Students should check whether their own Education benefits actually provide usable entitlements; they may also ask the teacher to verify GitHub Education/Team eligibility. After the permissions are obtained, set the six required checks, independent approval, dismissal of stale reviews, and a force-push prohibition, then read them back and validate with a real control PR.

Official basis (checked 2026-11-14): [Protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [GitHub plans](https://docs.github.com/en/get-started/learning-about-github/githubs-plans), [Education benefits](https://github.com/settings/education/benefits). The existence of an eligibility page does not mean this account has obtained the entitlement.

## One-time first adoption of PR #1 (bootstrap)

Bootstrap means **the engineering baseline is introduced under review for the first time**; it is not a seventh gate category, an auto-approval switch, or an exemption from the six gates. A new verifier cannot appear in the old base beforehand, so `BASE_VERIFIER_UPGRADE_REQUIRED` for PR #1 is genuinely retained; it is not rewritten to success. The teacher's original text requires real supervision and the six gates, and no clause was found that would allow this round's Hermes engineering fixes to be backdated as student prior approval. **If the course does not accept this shared initialization / known-failing baseline, confirm with the teacher first, do not merge PR #1, and do not claim that the final assessment is satisfied.** This does not prevent claiming work, requirements, Plan and test preparation.

### What the real person concretely does now

1. **Pin the review target.** Open [PR #1](https://github.com/537Lab/PaperTrace/pull/1), copy the latest full 40-character head SHA from Commits, and confirm that base is still the main the team expects and that no later unreviewed commits exist. Do not approve a stale revision that an older summary refers to.
2. **Check the limited scope.** In Files changed, review the six gates and the event/token boundaries, OpenCode default-deny and module scope, the shared contract / five module briefs, the untouched upstream and the AI disclosure; verify the real execution receipts under `artifacts/verification/`. Focus on confirming the requested materials / runtime dependency binding, the real approval order, and that a main push re-verifies the merge source rather than skipping because no number is present. Confirm that A–E business work is still left to the members.
3. **Verify what can and cannot be verified.** Re-run the affected offline checks, or verify receipts that match the current file SHAs; state explicitly that the complete upstream still FAILs/times out, that the 9 live items are unauthorized, that the real semantic evaluation has not been run, that the protection API returns 403, and that student D5 has not yet happened. Do not demand unapproved paid calls to force green lights. The acceptance boundary for the course's shared starting point / known-failing baseline is confirmed by a real student/teacher and its source is left in the PR; if it is unconfirmed, do not write "teacher approved".
4. **Real independent review.** A real person who did not take part in this implementation and has repository write permission submits it via PR → Files changed → Review changes → **Approve**. The body states the latest full head, what was actually checked, that only the engineering starting point and the remaining conditions above are accepted; AI re-checks are not counted as one's own checking, and no prior approval is backfilled. The prompt below may be used, but the facts must be filled in personally:
   ```text
   First engineering baseline adoption: PR #1, head <full SHA>.
   What I actually checked: <specific diff / execution or verified evidence>.
   Accepted scope: the shared development starting point, not the A–E business implementation or student D5 contributions.
   No prior test approval was fabricated; upstream FAIL / unauthorized live / real model evaluation / protection limits are retained as-is.
   Basis for applying the course's shared starting point and failing baseline: <real source; if unconfirmed, merging is not recommended yet>.
   Conclusion: <agree to adopt within this explicit boundary, or request changes>.
   ```
5. **The first merge is still performed by a person.** Confirm that the previous step is an independent APPROVE by a real person on the current head, that the course acceptance boundary is resolved, and that there are no changes/conflicts; then a maintainer uses **Create a merge commit → Confirm merge** on the same PR. Preserve history where possible; do not rebase or force-push; if conflicts must be fixed, sync the branch with main first, re-verify, and re-review, and do not smuggle unreviewed content into the merge. **This round's agent neither merges nor enables auto-merge.** Where the plan cannot enforce protection, this manual adoption must be declared explicitly as a one-time initial engineering decision, not misrepresented as all six red lights having passed; if the course requires everything green at this point too, stop at step 4 and let the teacher decide, without granting an exemption unilaterally.
6. **Check the first main push.** The code merged into main becomes the reviewed control program, and static/Schema/full regression/disclosure actually re-run; the approval and semantic checks replay evidence from the native merged PR and no longer report `missing-pr-number`. **The real prior approval/evaluation missing for PR #1 will still be BLOCKED/FAIL, full may still fail, and nothing turns green automatically.** These gaps are course facts that this process does not patch. Subsequent normal PRs use the already-adopted base verifier and pass by supplying real evidence, without repeating the initial bootstrapping loop.

## Clear responsibilities for future events

- **PR / review events:** read the control program from the exact base; verify that open PR's test approval, applicable semantic evaluation, static, Schema, full regression and newly added disclosure. A test proposal may be open/RED, and a red proposal is no reason to sign an approval on someone's behalf or implement early.
- **main push:** listens to main only, so that each feature push does not run redundantly with its PR. The adopted main control program checks the event before/after; approval/semantic are traced through GitHub commit → merged PR → original base/head and the same tree and the original evidence is re-verified; static/Schema/full regression/disclosure check the new main directly. Sourceless/ambiguous PRs, dismissed approvals, unapproved tests, wrong repo/SHA/tree, and force-push/delete/create main events are all rejected, and a missing PR number never becomes an unconditional pass.
- **Manual re-run:** `workflow_dispatch` supports main only, and the corresponding real merged PR must still be recovered; it is not an escape hatch for a direct push or missing evidence. The team should prefer Create a merge commit, sync main before approval, and avoid batching several PRs or conflict editing that makes the merge tree differ from the reviewed head.
- **Trust boundary:** a run on main means the code has been adopted, not that its quality has passed; remote review permissions and the absence of enforced branch protection still need human management. A candidate can modify the workflow itself, so pinning to base is not a tamper-proof certification system; the workflow diff must be reviewed, and tokens must never be handed to candidate tests or real models.
